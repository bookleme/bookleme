# 结论与证据（Conclusion–Evidence Binding）

> 本文说明 BookLeme 如何把「一条规则」与「它的证据」分开绑，以及为什么。

## 1. 问题：引用能找到 ≠ 结论被支持

BookLeme 原本把一条规则写成一个整体句子（`I_rephrase`），然后用一条逐字引文
（`R_quote`）当它的证据。逐字校验能保证**引文是真的**，但保证不了**整条结论
都被这句引文支撑**。

真实例子（microsoft.ai 的 RL infrastructure 页，编译成框架速查）：

> **规则**：按「存储精度」与「计算精度」分离设计：低精度只用于存储以省显存提速，
> 计算前反量化回高精度执行，并在学习器侧复现同样的量化流程。
>
> **引文**：`we selectively use MXFP8 for MoE weights and KV caches`

引文逐字命中，通过校验。但引文只说「**微软选择性用 MXFP8**」，没说「低精度只用于
存储」、没说「计算前反量化」、没说「在学习器侧复现」——那些是**产物侧的概括**。
读的人很容易把整句当成普遍规则，而它其实是**微软特定方案**的摘要。

同类问题还有：**把案例条件写成绝对边界**。

> **边界**：不适用于非 MoE 模型（无专家权重可省）。

原文只是在这个案例里没有 MoE 专家权重可省，不是「非 MoE 模型一律不适用」。

## 2. 做法：拆成三部分，各绑各的证据

每条规则拆成三部分，**分别判状态**：

| 部分 | 是什么 | 证据从哪来 | 状态取值 |
|---|---|---|---|
| **来源事实** | 原文明确说了什么 | 必须有逐字引文 | `supported` / `unverified` |
| **适用条件** | 这条事实成立的上下文 | 原文里的限定语 | `supported` / `partial` / `downgraded` |
| **生成的推论** | 我们从事实推出来的 | **是我们加的** | `supported`（复述）/ `partial`（推论） |

### 2.1 怎么判「是不是推论」

判定是**确定性**的（不依赖模型打分），三条信号：

1. **因果/结论性连接词** —— 「所以 / 因此 / 从而 / 意味着 / 可以据此」
2. **指令性措辞** —— 规则里有「要 / 须 / 先 / 别」而引文里没有（是我们加的执行指引）
3. **规则明显长于引文** —— 引文只能覆盖它自己的长度；规则长出一截，多出来的
   内容就是产物侧扩写的。阈值 1.1（长 10% 以上即算）。

强度分级（让 `partial` 也有区分度）：

| 超出倍数 | 强度 |
|---|---|
| ≥1.6 | high |
| ≥1.3 | medium |
| >1.1 | low |

实测 microsoft.ai 的 12 张卡：**10 medium + 1 low + 1 none**（none 那张是引文与
规则都含强结论、属复述）。

**保守取向**：判不准时标 `partial`。宁可多提示「这是推论」，不可让读者把我们的
概括当成原文原话。

### 2.2 怎么判「强结论要不要降级」

强结论标记词：「必须 / 只能 / 一律 / 总是 / 不适用 / 收益不成立 / 不可能 /
不会 / 绝对 / 永远 / 任何情况下 / 无一例外」以及英文的
`must / only / always / never / cannot / not applicable / guaranteed`。

处理原则：

- 原文**明确支持** → 保留，标 `supported`（别把好规则改弱）
- 原文**没支持** → 降级，改写为：
  > 「该案例主要讨论此场景，其他场景需要另行验证。」

降级同时把绝对表述软化：`不适用` → `不直接适用`、`收益不成立` → `该收益未经验证`。

判定「原文是否支持」的依据：**引文里也出现了强结论**（引文英文 `must`、规则中文
「必须」也算一致——只看两边是不是都在下强判断，不要求词形相同）。

### 2.3 产物里长什么样

每个分片末尾多一个块：

```
### 结论与证据的绑定

| 部分 | 内容 | 证据状态 |
| --- | --- | --- |
| 来源事实 | we selectively use MXFP8 for MoE weights and KV caches | 有引文支撑 |
| 适用条件 | 不直接适用于没有数值一致性问题的短程蒸馏精修……该案例主要讨论此场景，其他场景需要另行验证。 | 已降级（原文未明确支持该绝对表述） |
| 生成的推论 | 按「存储精度」与「计算精度」分离设计：低精度只用于存储以省显存提速…… | 部分支撑 / 属推论 |

- **来源事实**：逐字引文，可回原文逐字核对
- **适用条件**：原文未明确支持该绝对边界，已降级为「案例主要讨论此场景，其他场景需另行验证」
- **生成的推论**：由上述事实推出，原文未直说（超出引文 medium）
```

## 3. 出处可独立复核

产物里那行出处以前是：

```
出处：SRC-001 / seg-005 / char_range [12692, 12746) / 可信度 B
```

读者知道「第 5 段」，但**无法独立定位**：偏移相对哪个文件？那个文件在哪？
什么编码？归一化规则是什么？怎么回原文找这一段？

现在每个分片带一个「出处复核信息」块，给出四件事：

1. **来源链接** —— 回到原文
2. **内容哈希** —— 确认拿到的是同一份
3. **抓取时间** —— 材料可能已更新
4. **章节标题** —— 定位到具体小节

外加**偏移基准**（自己复现时必须用同一套口径，否则字符对不上）：

- 相对文件：编译期归一化全文（共享 IR 的 `full_text.txt`）
- 编码：UTF-8
- 计数单位：Unicode 码位（Python 字符），非字节
- 范围规则：左闭右开 `[start, end)`
- 归一化：仅剥除不可见/控制字符，并折叠康熙部首（U+2F00–U+2FDF）与 CJK 兼容
  表意文字（U+F900–U+FAFF）；**不做整篇 NFKC**

> 该文件只存在于编译期缓存，不随产物分发（版权纪律）。要复核请用下方 url +
> sha256 取回原文，自行套用同一归一化规则后按 segment 定位。

## 4. 原文案例 vs 本项目验证

**Rocket 在 checkpoint 后调整 learner，是微软系统的实现选择。** 你的项目用混合
引擎 —— 直接照搬会把别人的实现当通用结论。

传 `--project-context <json>`，产物顶部会多一段四段式结构：

```json
{
  "code_version": "abc123",
  "job_ids": "job-1, job-2",
  "test_scope": "单元测试 + 单作业试跑",
  "data_version": "s3://.../2026-11-25",
  "source_says": ["原文说 Rocket 在 checkpoint 后调整 learner 规模"],
  "project_evidence": ["我们的 learner 由 OmniRL 调度，配置项是 ..."],
  "verified": ["本地放置函数实测通过（job-1 日志）"],
  "pending": ["缺同权重逐 token 数据；一旦概率差异随精度变化则判断作废"]
}
```

渲染成：

- **Wiki 的说法**（原文在哪、适用于什么版本）
- **当前项目证据**（代码 / 配置 / 作业 / 日志）
- **验证结果**（实际运行了什么）
- **尚待验证**（缺什么、什么会推翻当前判断）

## 5. 真实任务评测

冒烟用例考的是**路由**（对不对、会不会编造）。真实任务考的是**能不能落地**。

```bash
bookleme run --input <书> --project-context ctx.json --real-tasks tasks.json
```

产物里多一份 `evals/real-task.md`，三条硬判据：

| 判据 | 检查什么 |
|---|---|
| `executable_verification` | 回答是否找到可执行验证（代码位置 / 配置项 / 作业 / 日志），而不只是复述规则 |
| `sim_vs_production` | 回答是否区分「原文/模拟的做法」与「本项目线上事实」 |
| `states_why_undecidable` | 回答是否说清**缺哪些数据**、**什么现象会推翻当前判断**（只写「建议进一步验证」不算通过） |

判据是**确定性检查**：读回答文本匹配必备要素，不需要模型打分。

## 6. 源材料新鲜度

Wiki 和代码会更新。产物写着「Rocket 在 checkpoint 后调整 learner」——那是
**编译当天**的微软做法。三个月后它可能已经过时，而产物里没有任何提示。

```bash
bookleme freshness                      # 检查源材料是否已变
bookleme freshness --source <新材料>    # 跟指定材料比
```

编译时会把源文件快照存到 `cache/<sha>/sources_snapshot/`，作为比对基准
（**不是** `sources.json` 里记的 sha256 —— 那个是本次抓取时写的，等于「当前」，
拿它比自己永远是「未变」）。

判定结果：

| 状态 | 含义 |
|---|---|
| `fresh` | 与编译时一致 |
| `changed` | 内容已变 → 给出差异 + **受影响的具体章节** |
| `unknown` | 拿不到当前材料（本地文件、离线） |
| `missing` | 记录里的文件已不存在 |

「受影响章节」按 `char_range` 定位（不用标题字符串搜——原文标题带 Markdown
标记 `## Controlling staleness`，而 segments 里存纯标题，用 `find` 会误判到
别的章节）。

差异展示的是**解出 JSON `content` 字段后的正文**（换行已还原）——直接按行比
会把整篇正文当一行，diff 粒度全丢。
